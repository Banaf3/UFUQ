# Test and validation strategy

## Test principles

Tests are evidence for separate claims: implementation correctness, scientific agreement, transaction safety, usable rendering, security/accessibility, and educational effect. A passing test in one category cannot substitute for another. Reference fixture code is independent from runtime domain code.

## Test layers and exact gates

| Layer | Required coverage | Release gate |
|---|---|---|
| Pure astronomy unit | Angle normalization, time/frame adapters, hour angle, horizontal ENU, Three mapping, Qibla, vector/bearing distance, singular/error cases | All boundary/property cases pass; missing AST-006 implementation-numerics tolerance fails configuration rather than using an invented constant |
| Independent astronomy reference | Fixed approved catalogue/time/observer/Qibla cases generated by pinned Astropy/USNO/domain references | Every case within its AST-006 operation-specific tolerance; missing tolerance or reference manifest fails the suite |
| BKT unit/sequence | Correct/incorrect equations, typed no-op/transition-only decisions, transition order, constraints, edge cases, report and mixed sequences, scaffold policy | Results meet the independently justified absolute/relative implementation tolerance; invalid sets rejected; no duplicate transition |
| Catalogue/schema | Source manifest, numeric ranges/units, IDs, flags, Unicode, review state, relationships, generated manifest/hash | 100% rows valid; zero duplicate IDs, unresolved edges/tasks, unapproved cultural records, non-finite required values, or checksum drift |
| Assessment/raycast | Center/edge/outside clicks, empty space, overlap priority, hidden/non-assessable objects, viewport/DPR/resize/camera changes, direction alternatives | Deterministic expected target/evidence in all fixed cases; hints do not alter the target or hitbox |
| API integration | Public/protected route declarations, capability/ownership, immutable scenario expiry/consumption/expected revision, typed validation, scoring, error mapping, progress/admin filtering | All positive and negative contract cases pass against the composed API with server-side recomputation; no scorer/target code is present in the browser bundle |
| MySQL transaction | Commit/rollback at each fault point, first-use provisioning, unique constraints, fixed lock order, SYS-001 deadlock/timeout retry, fingerprinted idempotency, mastery revision | Against the frozen MySQL/InnoDB profile: no partial attempt/model/scaffold unit; concurrent identical key+fingerprint requests produce exactly 1 decision; same key/different content conflicts; stale revision and concurrent cold start are safe; distinct current-revision requests form one serialized chain |
| Browser E2E | Login, scenario, 3D answer, feedback, retry/reconciliation, own progress, admin authorization, no-hint path | Critical journey passes the exact primary study-browser project; additional engine smoke/full coverage matches only the approved support claim and retained environment manifest |
| Visual regression | Approved scientific sky and scaffold states only; semantic assertions cover ordinary forms, error, progress, and admin screens | PERF-001 freezes environment/masks/region thresholds and update owner; every scientific/scaffold baseline change has manual review; no universal pixel ratio is assumed |
| Accessibility | Semantics, forms, keyboard/focus, zoom/reflow, contrast, reduced motion, status announcements, equivalent answer control | Zero automated serious/critical violations plus an ACC-001 WCAG 2.2 AA criterion/AT/browser/viewport matrix and signed manual checklist; claim is explicitly bounded |
| Performance | Render loop, long-frame diagnostics, raycast computation and where approved input-to-feedback timing on PERF-001 baseline | PERF-001 defines valid foreground/power/thermal runs, repetitions and algorithms; the report's `>=30 FPS` and `<100 ms` interpretations pass with retained raw traces and no correctness degradation |
| Security/privacy | Authn/capability/ownership, CSRF, session, injection/XSS, rate limit, logs, pending submission, exports, fixture-bypass, dependency/secret/config scan | Approved SEC-003 ASVS 5.0.0 profile complete with no unresolved release blocker; zero restricted PDF/extracted text, credentials, session values, or prohibited catalogue bytes in tracked/build artifacts |
| Backup/recovery | Database backup, restore, schema/config/version reconciliation | Successful restore to an isolated environment and replay of a known assessment chain within DEP-001 targets |

Statement/branch coverage is diagnostic, not the oracle. Pure astronomy, assessment, BKT, and adaptive-policy formula/decision modules target 100% branch coverage, with exclusions reviewed; a high percentage never waives fixed-reference or property tests.

## Fixed astronomical fixtures

Each fixture stores ID, purpose, observer geodetic datum/latitude/east-positive
longitude/elevation datum, UTC instant and original zone, source
catalogue/version/row, complete selected astrometry/reference epoch/uncertainties,
astronomy algorithm and EOP dataset/hash/approximation status, expected
intermediate/output values, oracle program/library/data versions and settings, error-
budget/tolerance IDs, generator author, independent reviewer, and approval date.

Required partitions include:

- object on/near meridian and east/west of it;
- 0/360° and ±180° wrap;
- UTC day boundary, leap date, and daylight-offset input resolved to the same instant;
- equator, approved Malaysian cities, high latitude, geometric horizon, below horizon, and near zenith;
- catalogue epoch, supported-date endpoints, high-proper-motion sample, and flagged/missing-data rejection;
- Qibla bearings from approved Malaysian locations plus a degeneracy/near-wrap case.

USNO and Astropy are cross-checks with stated limitations and exact pinned artifacts/settings. Near zenith, validate the vector because azimuth is undefined/unstable. Refracted cases are excluded until AST-004 and AST-006 explicitly approve their model and tolerance. High-latitude/high-proper-motion cases are reference robustness tests, not implied learner-scenario scope.

## BKT and adaptive tests

- Reproduce the `.60` report example and all sequences in `TUTORING_BKT_SPEC.md`.
- Exhaust parameter boundaries and randomized valid sets; condition strict posterior
  direction on interior priors and possible informative evidence, verify finite range and
  transition ordering, and retain seed/generator/case-count/minimized-failure metadata.
- Verify the low-mastery incorrect fixed-point behavior so DEV-008 cannot regress.
- Run every approved assisted-evidence option as an explicit policy fixture; no default branch.
- Verify threshold equality, crossing, restoration, independence status, authoritative
  server-issued cue snapshot versus untrusted render telemetry, and immutable policy
  version.
- Replay one stored attempt repeatedly and prove byte/equivalent response plus zero additional state transitions.

## API/database fault matrix

Inject failure before idempotency claim, after claim, after session/scenario/mastery lock,
after score, after attempt insert, after model/scaffold decision, before commit, and after
commit before response. The expected result is either a complete committed unit
returned on matching retry or no visible state. Test concurrent first-use provisioning,
same key with different evidence/endpoint/contract, wrong user/session/capability,
malformed/oversized payload, consumed/expired/stale-revision scenario, unsupported
versions, changed catalogue/EOP hash, missing tolerance, forged correctness/mastery/cue
fields, deadlock, lock timeout, and retry exhaustion.

Tests must use the supported MySQL/InnoDB engine—not SQLite or mocks—for lock and isolation assertions. Domain unit tests remain database-free.

## Raycasting and visual validation

Use a fixed camera matrix and generated catalogue fixture. Test pointer normalization at viewport edges, high DPR, canvas offset, resize, occlusion/overlap priority, label/line non-interference, and both pointer and approved keyboard/equivalent controls. A selected mesh produces only a stable catalogue/task ID; Three object references never cross the contract.

Screenshots use deterministic time, seed, fonts, catalogue, exact OS/browser/GPU/WebGL
renderer where feasible, no transition animation, and approved masks. Pixel gates are
diagnostic environment-specific thresholds; a human confirms scientific
labels/relationships and scaffold meaning. Ordinary form/dashboard behavior uses
semantic assertions instead of broad snapshot maintenance. Fake-clock and explicit
time-zone tests cover the default-current-time workflow.

## Educational evaluation

No participant study begins before EDU-001 and SEC-001 approval. Before recruitment,
the export schema, codebook, scoring and analysis implementation are exercised on a
synthetic frozen dataset; this is not participant evidence. The frozen EDU-001–005
protocol must include:

1. no-hint pre-test by KC;
2. guided/adaptive learning with actual assistance logged;
3. no-hint post-test using non-identical but equivalent approved scenarios;
4. immediate no-hint independent evidence and delayed recall only if approved/feasible;
5. correctness, angular error, completion time, assistance, retries, and BKT trajectory;
6. SUS with target mean `>=68`, plus clearly labelled qualitative feedback;
7. prespecified estimand/primary outcome, comparator or explicit non-causal boundary,
   participant-level analysis unit, sample-size/power rationale, multiplicity strategy,
   statistical tests/effect sizes/confidence intervals, missing-data/exclusion handling,
   and under-recruitment claim-reduction rule;
8. expert-reviewed task-to-KC mapping and non-identical-form equivalence procedure,
   with exposure/counterbalancing and practice-effect controls;
9. operational definitions for time, pauses, assistance exposure, retries/offline delay,
   abandonment, and server/client timestamps.

Report mathematical accuracy, software performance, usability, model behavior, and learning outcome separately. Do not infer learning effectiveness from frame rate, BKT fit, or SUS.

## Evidence retention

Each phase writes a non-sensitive evidence manifest under the location selected by its
ExecPlan. The manifest records evidence ID; requirement/risk IDs; exact command and
working directory; exit/result; commit and dirty-state disclosure; UTC; tool/runtime/OS;
browser revision; hardware/GPU/WebGL renderer where relevant; input catalogue,
scenario, software, EOP and policy hashes; raw-versus-derived artifact paths and
SHA-256; approval/sign-off; access/retention class; and clean-machine reproduction
steps. A tracked evidence index may point to protected research/licensed artifacts but
never contains them.

Test retries, quarantine, reruns, baseline updates, and intermittent WebGL/GPU failures
are disclosed in the manifest; a rerun never silently replaces the original result.
Research exports are pseudonymized and governed separately. Never retain credentials,
raw session cookies, restricted report text, or catalogue data beyond its licence.
